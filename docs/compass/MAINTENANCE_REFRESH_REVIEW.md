# 要求更新与短任务维护衔接修复

日期：2026-11-23。修改位置：Downloads/iCode-brief。仅修改 Compass 代码，不改 iCode 宿主。

## 本次问题

会话 4272f31385e6 的第一页缺陷修复任务，测试结果已经是 10/10，E-012 和退出码 0 均已记录。Agent 在两轮都调用了 Brief 工具。此前维护到 E-008；Agent 第二轮检查时只有 E-012，手动检查后到 E-015，均未达到累计 8 条新证据的测试窗口。要求重提取清空旧的覆盖关联，却没有新的维护重建关联，因此显示旧 Claims 和 no-evidence。

## 修复后的行为

- 普通宿主工具仍只排队记录，不自动调用模型、不额外开启主模型回合。
- 显式调用 update_compass_brief（包括 /compass 的第二步）时，有尚未处理的测试结果就进入维护判断的 test_result 分支，不再等待 8 条。失败测试也会进入重新评估，但不会被程序直接标成通过。
- 要求重提取后持久化 requirements_pending。下一次显式 Brief 检查在有证据时重新评估，即使没有任何新证据也能利用历史证据；不伪造新观察、不倒退证据游标、不把旧覆盖关系直接搬到新要求。
- 普通阅读等证据保留原批量窗口；没有证据时不会仅因要求重提取就调用维护模型。
- 只有维护成功且提交新记录才清除待重新评估标记。异常、取消或维护失败会保留它。无新内容的重复检查不重复维护。
- 旧 checkpoint 中已有 Claims、但要求覆盖为空的状态会恢复一次待重新评估标记；成功后保存标记，避免每次重启都重复。
- 状态页是只读的，不清队列、不维护。显示 Record revision（记录版本）、已处理证据位置、触发原因和还差多少证据；不能把要求更新产生的版本增加当作完成一次 Brief 维护。

## 代码位置与边界

| 文件 | 改动 |
| --- | --- |
| gate/controller.py | 产品工具的触发判断、待重新评估标记、旧 checkpoint 恢复、结果诊断字段 |
| session.py | 新增默认 False 的 reassess_requirements 可选参数并向下传递 |
| claims/maintenance.py | 仅在该选项开启时允许“无新 delta、有要求变更”的维护，仍走原证据检索和提交验证 |
| adapters/icode/tools.py | 提示模型在最终测试后、回答完成前调用 Brief 工具；不强制接管执行循环 |
| adapters/icode/commands.py、tui/command.py、tui/status.py | 返回与展示真实维护判断、证据游标和记录版本 |
| provenance.json | 保留原哈希，登记两处核心支持改动及新哈希 |

这是本轮增量；此前分支的宿主接线不在本轮改动中。独立评测入口不启用新参数，原 8 条窗口常量未改。要求提取、Claim 生成、冲突判断和模型自身输出质量没有在本轮改写。并非保证每项要求都获得支持；证据不足仍应显示未验证。
