# 用户原文捕获与探索后更新（2026-11-20）

## 现在怎么用

用户：给登录接口加限流，并保持现有返回格式。

1. iCode 开始用户回合时，Compass 自动保存回合上下文提供的原始文字，不让主模型改写成任务参数。这一步不调用模型、不生成要求。
2. 主模型调用 `update_compass_requirements()`，无需参数，生成初版 Goal、Requirements、Constraints。
3. 主模型使用原生工具探索相关代码，实际工具输出被记录为 Evidence。
4. 再调用 `update_compass_requirements()`：用户要求相同，但仓库上下文增加，允许重新提取，明确涉及哪些文件、函数和已有兼容约束。
5. 立即再调用一次，没有新用户输入，也没有仓库上下文变化，就直接返回现有记录，不再次调用提取模型。

“先调用、探索、再调用”写进工具说明和 Extension 提示。调用仍由主模型选择，不通过 runner 强制安排；捕获原文是自动的，模型提取由工具调用触发。仓库上下文沿用 core 原来的有界观察摘要，不代表已经扫描整个仓库。

用户后续补充的原文按回合顺序保留，与原任务一起用于提取。不会用一句“也支持空字符串”替换之前的完整任务。同一回合的重试按原生 invocation ID 去重。这里只保存回合上下文实际提供的文本，不宣称额外读取附件全文或捕获全部回合中途注入。

## 去重边界

- 用户原文或有界仓库上下文任意一项改变，都允许重新提取。
- 提取失败走原有 fallback，不把失败记为成功缓存；下次显式调用仍能尝试。
- 成功恢复 fallback 后，缓存对应的文本和仓库上下文。
- 存档保留成功提取的输入组合；旧存档缺此字段仍可载入，首次显式更新会重新提取。
- 存档中的新字段先校验类型，再恢复现场；不因损坏的缓存静默跳过要求提取。
- 更新仍走原有 `start(revise=True)`：保留 Claims/Evidence，重置旧的 requirement coverage。它不是自动追加更多用户需求，仓库材料只能解释、定位和约束原任务。
